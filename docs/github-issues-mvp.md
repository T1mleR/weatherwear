# GitHub Issues: WeatherWear AI

Бэклог по итерациям. Лейблы: `MVP`, `Post-MVP`, `User-Test-Bug`.

Формат задач следует ролям:

- PM: Goal / Description / Acceptance Criteria
- QA: Test Scenario / Steps / Expected Result
- Architect: Mock → OpenAPI → In-Memory → SQLite

---

## MVP

### Issue 1 — Mock-экран совета по одежде

- Labels: `MVP`

## Goal
Пользователь видит пример погоды и совет по слоям без реальных API.

## Description
Собрать первый экран WeatherWear на фикстурах: город, температура, условие погоды, слои base/mid/outer и короткий комментарий.
Out of scope: OpenAPI, серверная логика, SQLite, геолокация.

## Acceptance Criteria
- [ ] На главной странице отображается выбранный mock-город и текущая температура.
- [ ] Показаны минимум три зоны совета: base, mid, outer.
- [ ] Есть текстовое обоснование, связанное с погодой.
- [ ] Нет запросов к внешнему weather API.

---

### Issue 2 — Контракт OpenAPI для погоды и outfit

- Labels: `MVP`

## Goal
Команда работает по одному контракту API, а не по устным договорённостям.

## Description
Описать в `docs/openapi.yml` эндпоинты получения погоды и рекомендации по одежде, схемы слоёв и ошибок.
Зависит от Issue 1. Не реализовывать persist.

## Acceptance Criteria
- [ ] В `docs/openapi.yml` есть путь запроса рекомендации (город обязателен).
- [ ] Схема ответа содержит weather + layers + summary.
- [ ] Описаны ошибки 400 (невалидный город) и 404 (город не найден).
- [ ] Поля слоёв совпадают с тем, что уже показывает mock-UI.

---

### Issue 3 — In-memory генерация слоёв

- Labels: `MVP`

## Goal
Совет считается правилами, а не зашит одним статичным текстом.

## Description
Реализовать API по OpenAPI: на вход город (и опционально активность), на выход погода из stub и слои по правилам температуры/осадков/ветра. Хранилище — память процесса.
Out of scope: SQLite, реальный weather provider.

## Acceptance Criteria
- [ ] Запрос с известным городом возвращает 200 и слои.
- [ ] При t ≤ 0 outer содержит утепление.
- [ ] При осадках совет включает защиту от влаги или зонт.
- [ ] Неизвестный город возвращает ошибку, описанную в OpenAPI.
- [ ] После перезапуска сервера in-memory история может быть пустой — это ожидаемо.

---

### Issue 4 — Подключение SQLite для истории советов

- Labels: `MVP`

## Goal
Пользователь не теряет последние рекомендации после перезапуска.

## Description
Сохранять в SQLite город, снимок погоды, слои и время запроса. UI показывает последние N советов.
Делать только после in-memory этапа.

## Acceptance Criteria
- [ ] Новый успешный совет пишется в SQLite.
- [ ] После рестарта приложения последние записи на месте.
- [ ] Схема не торчит в UI: клиент ходит только в OpenAPI.
- [ ] Ошибка БД не роняет страницу, показывается понятное сообщение.

---

### Issue 5 — Пустые и ошибочные состояния UI

- Labels: `MVP`

## Goal
Пользователь понимает, что делать, если города нет или погода не пришла.

## Description
Добавить состояния: загрузка, невалидный ввод, город не найден, сервер недоступен.

## Acceptance Criteria
- [ ] Пустой ввод города нельзя отправить без подсказки.
- [ ] 404 показывается человеческим текстом.
- [ ] Во время запроса виден индикатор загрузки, старый outfit не выдаётся за новый.

## Post-MVP

### Issue 6 — Реальный погодный провайдер

- Labels: `Post-MVP`

## Goal
Совет строится на живой погоде, а не на stub.

## Description
Заменить stub адаптером внешнего weather API, сохранив OpenAPI. Нужен кэш и таймаут.
Out of scope: аккаунты.

## Acceptance Criteria
- [ ] Для реального города приходит актуальная температура.
- [ ] Провайдер спрятан за адаптером; UI не знает имя внешнего сервиса.
- [ ] Таймаут/5xx превращаются в ошибку контракта, UI показывает fallback.

---

### Issue 7 — Контекст активности (учёба, офис, спорт, прогулка)

- Labels: `Post-MVP`

## Goal
Совет меняется в зависимости от того, куда идёт пользователь.

## Description
Добавить в запрос поле activity и правила: спорт — меньше слоёв/больше свободы движения, офис — нейтральный дресс-код.

## Acceptance Criteria
- [ ] Activity отражено в OpenAPI.
- [ ] Один и тот же город даёт разный outer/base для `sport` и `office`.
- [ ] Если activity не передана, используется default `outdoor`.

---

### Issue 8 — Предпочтения пользователя

- Labels: `Post-MVP`

## Goal
Человек, которому всегда холодно или всегда жарко, получает сдвиг слоёв.

## Description
Хранить в SQLite простые предпочтения: freeze-bias / heat-bias, нелюбовь к определённым вещам.

## Acceptance Criteria
- [ ] Включение «мне всегда холодно» добавляет слой или более тёплый outer при той же погоде.
- [ ] Предпочтения переживают рестарт.
- [ ] Без предпочтений поведение MVP не меняется.

---

### Issue 9 — Геолокация вместо ручного города

- Labels: `Post-MVP`

## Goal
Пользователь получает совет для текущего места без ввода города.

## Description
Опциональная кнопка «моя геолокация». Отказ в разрешении не блокирует ручной ввод.

## Acceptance Criteria
- [ ] При разрешении координаты превращаются в город/локацию и уходят в существующий API.
- [ ] При отказе остаётся поле города.
- [ ] Нет хранения координат, если пользователь об этом не просил.

### Seed checks (ещё не баги, чеклист приёмки)

#### UTC-1. Слои противоречат жаре

## Test Scenario
Город с mock/stub температурой +28°C без осадков.

## Steps
1. Запросить совет для жаркого сухого дня.
2. Прочитать base / mid / outer.

## Expected Result
Нет зимней парки в outer. Mid может быть пустым или явно «не нужен».

---

#### UTC-2. Дождь не отражён в совете

## Test Scenario
+10°C и дождь.

## Steps
1. Запросить совет для дождливой погоды.
2. Проверить extras и outer.

## Expected Result
Есть мембрана, дождевик или зонт.

---

#### UTC-3. Невалидный город в UI

## Test Scenario
Пользователь вводит пустую строку или набор символов «asdfgh».

## Steps
1. Открыть форму города.
2. Отправить пустое значение.
3. Отправить «asdfgh».

## Expected Result
Пустой ввод блокируется до запроса. Неизвестный город даёт понятную ошибку, экран не падает.

---

#### UTC-4. История после рестарта

## Test Scenario
SQLite-этап, пользователь уже получил хотя бы один совет.

## Steps
1. Сгенерировать совет.
2. Перезапустить приложение.
3. Открыть историю.

## Expected Result
Последняя запись на месте, слои совпадают с тем, что было до рестарта.
